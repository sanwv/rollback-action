# Rsync Rollback

[English](README.md) | [简体中文](README.zh-CN.md)

A GitHub Composite Action that rolls back deployments created by [`sanwv/deploy-action`](https://github.com/sanwv/deploy-action). It switches the remote `current` symlink to an existing release over SSH. It does not build, upload, or delete releases.

## How it works

The deployment target must use this layout:

```text
/srv/www/my-site/
├── current -> releases/<release-id>
├── releases/
│   ├── <release-id>/
│   └── ...
└── shared/
```

The Action obtains the same remote lock used by `sanwv/deploy-action` (`<target>/.deploy.lock`), checks the active release and target, then atomically replaces `current` with a temporary symlink. If the post-switch hook fails, it restores the prior symlink before releasing the lock. A rollback never removes releases.

The `steps` mode orders release directory names lexically. This matches the UTC timestamp prefix generated by `sanwv/deploy-action` (`YYYYMMDDTHHMMSSZ-<run-id>-<attempt>`), and does not depend on directory modification times. Use `release_id` when selecting an exact release.

## Use with `sanwv/deploy-action`

[`sanwv/deploy-action`](https://github.com/sanwv/deploy-action) creates the release directories this Action rolls back to. Configure both Actions with the same SSH host, user, and `target`. The deploy Action's `releases_to_keep` setting determines how many prior releases remain available; rollback cannot restore a release that deployment has pruned.

Both Actions take the remote `<target>/.deploy.lock`, which serializes rollback with activation and release pruning. Also use the same GitHub Actions concurrency group in deployment and rollback workflows, with `cancel-in-progress: false`. For deployment inputs, shared files, build examples, and retention configuration, see the [deploy Action README](https://github.com/sanwv/deploy-action#readme).

## Inputs and outputs

| Input | Required | Default | Description |
|---|---:|---:|---|
| `ssh_private_key` | Yes | — | SSH private key. Pass as a GitHub Secret. |
| `ssh_host` | Yes | — | SSH target: `user@host` or `user@host:port` (default port `22`; bracket IPv6 addresses). |
| `target` | Yes | — | Remote deployment root, not the `current` directory. |
| `ssh_known_hosts` | No | Empty | Verified `known_hosts` entry. If empty, SSH uses `accept-new`. |
| `release_id` | No | Empty | Exact release to activate. Mutually exclusive with `steps`. |
| `steps` | No | `1` when `release_id` is empty | How many older retained releases to move from the active release. Range: `1`–`100`. |
| `script_before` | No | Empty | Remote Bash script run in the target release before switching. |
| `script_after` | No | Empty | Remote Bash script run after switching. If it fails, the Action restores the previous release. |

Outputs `previous_release` and `release_id` contain the release that was active before rollback and the release activated by this run.

Hook scripts receive these environment variables: `ROLLBACK_TARGET`, `ROLLBACK_CURRENT_RELEASE`, `ROLLBACK_RELEASE_ID`, `ROLLBACK_RELEASE_PATH`, and `ROLLBACK_HOOK` (`before` or `after`).

## Setup

Add these repository Actions settings:

| Name | Type | Description |
|---|---|---|
| `SSH_PRIVATE_KEY` | Secret | Private key authorized on the server. |
| `SSH_KNOWN_HOSTS` | Optional Secret or Variable | Verified server host key. |
| `SSH_HOST` | Variable | SSH target, e.g. `deploy@example.com:2222`; port defaults to `22`. |

The server needs Bash, `flock`, `realpath`, `find`, `sort`, and standard GNU/Linux utilities. The SSH user must be able to read the releases, create symlinks, and write `<target>/.deploy.lock` and `<target>/current`.

## Examples

### Roll back one release

```yaml
name: Rollback production

on:
  workflow_dispatch:

# Use the same group in your deployment workflow. Do not cancel an active deployment.
concurrency:
  group: production-deploy
  cancel-in-progress: false

jobs:
  rollback:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: sanwv/rollback-action@v2
        id: rollback
        with:
          ssh_private_key: ${{ secrets.SSH_PRIVATE_KEY }}
          ssh_known_hosts: ${{ secrets.SSH_KNOWN_HOSTS }}
          ssh_host: ${{ vars.SSH_HOST }}
          target: /srv/www/my-site
          steps: 1
      - run: echo "Rolled back from ${{ steps.rollback.outputs.previous_release }} to ${{ steps.rollback.outputs.release_id }}"
```

### Choose a release from the Actions UI

```yaml
name: Roll back to selected release

on:
  workflow_dispatch:
    inputs:
      release_id:
        description: Exact release ID to activate
        required: true
        type: string

concurrency:
  group: production-deploy
  cancel-in-progress: false

jobs:
  rollback:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: sanwv/rollback-action@v2
        with:
          ssh_private_key: ${{ secrets.SSH_PRIVATE_KEY }}
          ssh_host: ${{ vars.SSH_HOST }}
          target: /srv/www/my-site
          release_id: ${{ inputs.release_id }}
```

### Roll back two releases and check health

```yaml
- uses: sanwv/rollback-action@v2
  with:
    ssh_private_key: ${{ secrets.SSH_PRIVATE_KEY }}
    ssh_host: ${{ vars.SSH_HOST }}
    target: /srv/www/my-site
    steps: 2
    script_after: |
      curl --fail --max-time 10 http://127.0.0.1/health
```

A failed post-switch hook causes the symlink to be restored and the Action to fail. This rollback only changes application code selection; it does not reverse database migrations, shared files, queues, or other external state.

## Repeated rollback and edge cases

Given retained releases A, B, C in old-to-new order, with C active, `steps: 1` activates B. Running it again activates A. Running it when A is active fails with `no older release available` and leaves `current` unchanged. The same happens if the requested depth exceeds the retained history. If the requested exact release is already active, the Action succeeds as a no-op.

The maximum rollback depth is limited by releases retained by the deploy Action's `releases_to_keep` setting. Configure that retention count to cover the number of releases you need to recover to. A removed release cannot be recovered by this Action.

Deployment and rollback workflows should share a GitHub Actions concurrency group, and the Action also uses the shared server-side lock. See [GitHub deployment concurrency](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).
